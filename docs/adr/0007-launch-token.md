# The Studio Server only answers holders of a Launch token

The Studio Server can launch any command and returns saved credentials, so loopback alone is not enough. Each launch generates a random 256-bit token (`STUDIO_TOKEN` fixes it for scripts and tests). The CLI prints and opens `http://localhost:<port>/?token=…`. The page removes the token from the current URL and history entry with `history.replaceState`, preserving other query parameters and the fragment. It checks the candidate with its own Bearer header against `/api/health` and replaces the `localStorage` token only on success; a rejected candidate leaves the stored token intact. Reloads and new tabs on the same origin reuse the stored token. A restart replaces the token; rejected credentials show a help page asking the user to open the new link printed in the terminal.

**Cookies are not port-scoped.** Our earlier `HttpOnly; SameSite=Strict` cookie named `mcp_studio_<port>` separated cookie names, but browsers still sent its secret to every app on `localhost`, regardless of port. An unrelated localhost app could capture and replay it. No cookie flag fixes this. We therefore removed cookie authentication entirely and expire the legacy cookie when a request carries it. A request with only the old cookie always gets `401`. `localStorage` is scoped to scheme + hostname + port: another localhost port neither receives the credential automatically nor can read Studio's storage. Scripts on Studio's own origin can read it; those scripts and the same-origin policy are part of the trust boundary. This protects against unrelated browser origins, not processes that can inspect the browser profile or Studio's memory.

HTML and static assets are public and contain no data or embedded credentials. Every REST request (including `/health` and the `/api` aliases) sends `Authorization: Bearer <token>`. Query tokens never authorize API requests. The browser WebSocket authenticates **during the handshake**, offering `Sec-WebSocket-Protocol: mcp-studio, token.<token>`. The Studio Server validates the token before upgrading and echoes only `mcp-studio`, never the secret. Script clients may instead use the Bearer header for the upgrade. Unauthorized REST calls and upgrades return `401`. Exact Origin and `Host:port` checks still apply, including to public assets; `OPTIONS` preflights carry no data and need no credential.

All browser REST callers share the credential wrapper. Any REST `401` immediately replaces the app with terminal help, even after the app mounted. WebSocket connections recheck `/api/health` before each handshake/reconnect, and after errors or unexpected closure, because browser WS errors hide the handshake's HTTP status. A `401` from that check also locks the app. Focus, online and Launch token storage changes recheck idle tabs; a successful check also unlocks a previously locked tab. Network failures remain connection errors; they do not imply expired credentials.

`/oauth/callback` is the authentication exception: the single-use random OAuth `state` authenticates the authorization server's redirect (ADR-0006), and its response is fixed text.

The Studio Server listens on both `127.0.0.1` and `[::1]` on the same port, so another local user cannot squat the IPv6 loopback and receive traffic for `localhost`; a taken `[::1]` port stops startup, and a host without IPv6 runs on `127.0.0.1` alone.

Every response carries `Content-Security-Policy` (`default-src 'self'`, no inline script, `frame-ancestors 'none'`, `img-src 'self' data: https:`, `connect-src 'self' ws://localhost:* ws://127.0.0.1:*`, `object-src 'none'`, `base-uri 'none'`), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`. The theme bootstrap is a static file (`/theme-init.js`) and fonts are bundled. Two deliberate CSP exceptions remain: `style-src 'unsafe-inline'` (Radix and Sonner inject styles) and `script-src 'unsafe-eval'` (Ajv compiles output-schema validators with `new Function`); dropping the latter needs a non-compiling validator.

Bun's development error page is disabled; unexpected errors return a generic `500`, malformed JSON bodies a `400`. WebSocket parsing and dispatch share a try/catch. Frames are validated against the `ClientMessage` shapes using type checks, never coercion of untrusted JSON values: malformed shapes receive `PROTOCOL_ERROR` and the Session keeps running. `CORS_ORIGIN` must be one exact `http(s)` origin (never `null` or `*`).

Development uses the same scheme. `bun dev` stores one token in the gitignored `apps/server/.dev-token` so watch restarts keep the browser authenticated; both newly created and reused files have mode `0600`, enforced before reading a reused token. The printed `http://localhost:3000/?token=…` link redirects with its query intact to the Vite origin on `5173`. That page consumes and cleans it into its own origin's storage. Vite's `/api` proxy forwards the Bearer header, and the direct `ws://localhost:3000/ws` connection offers the token in its handshake. No cross-port cookie is needed.
