# The Studio Server only answers holders of a Launch token

The Studio Server can launch any command and returns every saved credential, so loopback alone is not enough: any local process or OS user, and any page that frames Studio, could drive it. Like Jupyter, each launch generates a random 256-bit token (`STUDIO_TOKEN` fixes it for scripts and tests). The CLI prints and opens `http://localhost:<port>/?token=…`; the server checks it, sets an `HttpOnly; SameSite=Strict; Path=/` cookie named `mcp_studio_<port>` (cookies are not port-scoped, so the port keeps concurrent Studios apart) and redirects with `303` to the same URL without the token, so it never stays in the address bar or history. Every route, including static files, `/health`, the `/api` alias and the `/ws` upgrade, needs that cookie or `Authorization: Bearer <token>`. Without it a page load gets a minimal help page (no script, no app shell, no data) telling the user to open the printed link, and an API call gets a plain `401`. Origin and exact `Host:port` checks still apply on top. `OPTIONS` preflights answer without the token because they carry no data.

`/oauth/callback` is the one exception: the authorization server's redirect is a cross-site navigation, so the `SameSite=Strict` cookie never arrives. The single-use, random OAuth `state` authenticates it instead (ADR-0006), and its response is fixed text.

We chose a cookie over a token the SPA holds in `sessionStorage` and attaches itself, because the cookie also covers the page, static assets and the WebSocket handshake without app code, and `HttpOnly` keeps it away from any script. A new tab in the same browser therefore just works, while another browser, user or process does not. Restarting Studio invalidates open tabs; they show the help page until the new link is opened.

The server listens on both `127.0.0.1` and `[::1]` on the same port, so another local user cannot squat the IPv6 loopback and receive traffic for `localhost`; a taken `[::1]` port stops startup, and a host without IPv6 runs on `127.0.0.1` alone.

Every response carries `Content-Security-Policy` (`default-src 'self'`, no inline script, `frame-ancestors 'none'`, `img-src 'self' data: https:`, `connect-src 'self' ws://localhost:* ws://127.0.0.1:*`, `object-src 'none'`, `base-uri 'none'`), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`. The theme bootstrap is a static file (`/theme-init.js`) rather than an inline script, and fonts are bundled instead of loaded from Google Fonts. Two deliberate CSP exceptions remain: `style-src 'unsafe-inline'` (Radix and Sonner inject `<style>` at runtime) and `script-src 'unsafe-eval'` (Ajv compiles output-schema validators with `new Function`); dropping the latter needs a non-compiling validator.

Bun's development error page is disabled; unexpected errors return a generic `500`, malformed JSON bodies a `400`. WebSocket frames are validated against the `ClientMessage` shapes before dispatch: any other JSON gets a `PROTOCOL_ERROR` reply and the Session keeps running. `CORS_ORIGIN` must be one exact `http(s)` origin (never `null` or `*`) because that origin gets full control, including launching commands.

Development keeps the same rules: `bun dev` stores one token in the gitignored `apps/server/.dev-token` (mode 0600) so `--watch` restarts keep the browser signed in, and prints `http://localhost:3000/?token=…`, which redirects to the Vite dev server after setting the cookie. Vite's `/api` proxy forwards the cookie, and the direct `ws://localhost:3000/ws` connection sends it because the cookie is not port-scoped.
